## 게이트: `run_gate("v2", "v3-base")` → **FAIL**

## 빔 후보와 안전장치

`metadata.json`의 `decoding.num_beams`는 생략하면 1(기존 탐욕 디코딩)이다. 4로 바꾼 모델은 매 토큰 단계에서 살아 있는 빔을 한 번에 추론하고, 점수는 길이 정규화(log probability ÷ 생성 길이)로 비교한다. 빈 출력과 원문 길이의 50%보다 짧은 출력은 후보에서 제외한 뒤 숫자·보존 용어 검사를 통과하는 가장 높은 점수 후보를 사용한다. 상위 빔 수만큼 완료 후보가 살아 있는 빔보다 점수가 높아지면 탐색을 끝내며, 완료 후보는 KV 캐시를 보관하지 않는다. 전부 실패하면 원문을 반환하고 첫 실패 사유를 기록한다.

`training.export`는 같은 KoBART 체크포인트의 `generate(num_beams=N)` 결과와 ONNX 서빙 출력을 비교한 뒤에만 parity 기준을 쓴다. 재생성 스크립트도 HF 체크포인트를 기준으로 비교하고 불일치면 기존 `parity.jsonl`을 덮어쓰지 않는다. 모델 폴더의 `hf/`가 기준 체크포인트다:

```bash
python -m training.export --version v3-base --num-beams 4
python scripts/regenerate_parity.py v3-base --models-dir models --hf-dir models/v3-base/hf
python -m gate.parity v3-base --models-dir models
python scripts/benchmark_decoding.py models/v3-base data/eval/eval_set.jsonl --num-beams 4
```

벤치마크는 greedy와 지정 빔 수의 문장당 p95 및 프로세스 최대 RSS를 각각 출력한다. 같은 모델·평가셋·반복 횟수로 비교하고 CPU p95 1,000ms 이하, peak RSS 300 MiB 이하인지 본다. Parity를 다시 만들면 학습 환경에서 `HF generate(num_beams=N)`와 비교하고, 서버에서는 `python -m gate.parity ...`로 그 기준을 검사한다.
