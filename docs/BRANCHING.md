# 브랜치·이슈·PR 규칙

## 흐름 (GitHub Flow)
1. **이슈 하나 = 작업 하나.** 템플릿으로 만들고 `agent:*`, `type:*` 라벨을 붙인다.
2. **브랜치**는 `main`에서 만든다. 이름은 `<에이전트>/<이슈번호>-<짧은-설명>` (예: `codex/3-router-gate`). 에이전트: `claude`, `codex`, `max`.
3. 작업하며 자주 커밋한다. 커밋 메시지 끝에 `Refs #<이슈번호>`.
4. 끝나면 **PR**을 연다. 본문에 `Closes #<이슈번호>`. 총괄이 리뷰한다.
5. **CI(`test`)가 통과하면 병합**한다. 사람 승인은 필수가 아니다(1인 프로젝트).
6. 병합은 **squash**: 작업 하나가 `main`에 커밋 하나로 들어간다. 문제가 생기면 그 커밋 하나만 되돌리면 된다. 병합한 브랜치는 지운다.

## main
- 항상 배포할 수 있는 상태. 직접 push하지 않는다(브랜치 보호로 CI 통과 필수).
- 서버 배포는 `main`에 태그 `v0.<기능>.<수정>`를 달 때 실행한다(T10에서 연결).
- 모델 버전(`v1`, `v2` …)은 코드 버전과 별개다. 모델은 `registry.json`으로 배포·롤백한다.

## 브랜치가 이어질 때
앞 작업이 아직 병합 전인데 이어서 해야 하면 앞 브랜치에서 만들고, PR의 base를 앞 브랜치로 둔다. 앞 PR이 병합되면 base를 `main`으로 바꾼다.

## 같은 파일 동시 수정 금지
에이전트마다 별도 git worktree에서 작업한다. 같은 파일을 두 PR이 동시에 고치지 않게 이슈를 나눈다.
